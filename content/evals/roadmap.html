Sixty years of asking: is it any good?

Every metric below is still in use somewhere in a modern AI stack, and almost none of them were invented for AI. Retrieval evaluation is a 1966 idea running underneath your vector database. Precision and recall are the reason your agent's tool router can be scored at all. The field didn't replace its methods — it stacked them. Read it in order once, then use the filter as a lookup.

module 0

How to think about evals

Before any formula: an eval is a measurement instrument, and instruments have their own error. Half of senior-level interview credit comes from showing you know the instrument can be wrong, not from reciting metric names.

The three levels, and why you need all three

Level 1 — component. Retriever nDCG, tool-selection F1, classifier AUC. Fast, cheap, deterministic, runs in CI on every commit. Tells you what broke.

Level 2 — task. End-to-end success on a golden set of realistic user goals. Slower, model-graded, run nightly or per-release. Tells you whether the change helped.

Level 3 — product. Deflection rate, human escalation, edit distance from the human's final version, cost per resolved ticket, CSAT. Runs in production. Tells you whether it matters.

Component metrics can improve while task metrics fall — a reranker that raises nDCG@10 by pushing a near-duplicate to rank 2 gives the generator no new information. Always name this in an interview; it's the single most common real-world failure and interviewers listen for it.

Goodhart's law is the background hum

"When a measure becomes a target, it ceases to be a good measure." Every layer below has its own Goodhart failure: BLEU rewards n-gram overlap so models learn to parrot; LLM judges reward length so models pad; SWE-bench leaks into pretraining so scores rise without capability. The defensive practices — held-out private slices, canary strings, adversarial sets, periodic re-baselining against human labels — are the same at every layer.

"Where would you start if we handed you an LLM feature with no evals at all?"

Answer the order, not the metrics. 1) Collect 50–100 real traces from prod or from the people who'll use it. 2) Read them by hand and build an error taxonomy — you will find 4–8 recurring failure modes, and that taxonomy is your eval spec. 3) Write binary assertions for the deterministic ones (schema valid, citation present, refused correctly). 4) Write an LLM judge only for the modes assertions can't catch, and validate that judge against ~100 human labels before you trust a single number from it. 5) Freeze it as a golden set in CI, then add online guardrails. Anyone who opens with "I'd compute RAGAS faithfulness" has skipped the part that actually determines success.

1966–1999

Information retrieval: where all of it starts

Cyril Cleverdon's Cranfield experiments (1960s) established the paradigm still in use today: a fixed document collection, a fixed set of queries, human relevance judgements, and a metric computed over the ranked list. NIST's TREC (1992) industrialised it. Every retrieval number in your RAG pipeline is a Cranfield number.

The confusion matrix and its children

Precision · Recall · Fβ Kent et al. 1955; Van Rijsbergen 1979 for F

Precision is "of what I returned, how much was right." Recall is "of what was right, how much did I return." They trade off: returning everything gives recall 1.0 and precision ≈ 0.

P = TP / (TP + FP) — purity of the returned set R = TP / (TP + FN) — coverage of the relevant set Fβ = (1 + β²) · P·R / (β²·P + R) β = 1 → F1, the harmonic mean. β = 2 → recall weighted 2× (screening). β = 0.5 → precision weighted 2× (when a false positive is expensive).
whereSet retrieval, classification, tool-selection scoring, entity extraction, guardrail classifiers.
whenThe output is a set, order doesn't matter, and you have binary labels.
whyIt splits the two ways of being wrong. Accuracy hides both; F1 forces you to say which error you fear.

F1 is the harmonic mean, so it collapses toward the worse of the two. And the harmonic mean of precision and recall has no natural interpretation — it is a convenience, not a truth. When positives are ~1% of the data, report PR-AUC or MCC alongside it.

Precision@k · Recall@k · R-Precision

Cut the ranked list at k and compute precision/recall on the top-k only. R-Precision sets k = number of known relevant documents for that query, making it self-normalising.

P@k = (# relevant in top-k) / k R@k = (# relevant in top-k) / (total # relevant) R-Prec = P@R, where R = |relevant set for this query|
whereThe primary retriever metric in RAG. k = number of chunks you actually stuff into the prompt.
whenYou have a hard budget on how many results the downstream consumer can absorb.
whyA user (or a context window) only sees the top few. Precision below rank k is irrelevant to both.

P@k is insensitive to ordering within the top k, and is capped when a query has fewer than k relevant docs. For RAG specifically, Recall@k is usually the metric that matters — if the answer-bearing chunk isn't in the context, no amount of generator quality saves you. Precision matters second, as a distraction/cost control.

Average Precision · MAP TREC-era standard

Average Precision averages P@k at every rank where a relevant document appears — rewarding systems that put relevant items early. MAP is the mean of AP across queries.

AP = (1 / |R|) · Σk=1..n P@k · rel(k) rel(k) ∈ {0,1} MAP = (1 / |Q|) · Σq∈Q AP(q) Example, relevant at ranks 1, 3, 4 out of 3 total relevant: AP = (1/1 + 2/3 + 3/4) / 3 = 0.806
whereClassic IR leaderboards, recommender offline eval, any binary-relevance ranking task.
whenRelevance is binary and you care about the whole ranked list, not just the top slot.
whySingle number, rank-sensitive, well understood. Strongly correlated with user satisfaction in navigational search.

MAP assumes binary relevance. If your labels are graded (perfect / good / marginal / irrelevant), you're throwing information away — use nDCG.

MRR — Mean Reciprocal Rank

Only the position of the first correct result counts.

MRR = (1 / |Q|) · Σq 1 / rankfirst-relevant(q) rank 1 → 1.00 rank 2 → 0.50 rank 3 → 0.33 rank 10 → 0.10 No relevant result found → contribute 0.
whereQuestion answering, "known-item" search, autocomplete, tool/function selection, entity linking.
whenExactly one right answer exists and the user stops as soon as they find it.
whyCheap to compute, needs only one label per query, and directly models "how far did I have to scroll."

MRR ignores everything after the first hit — a system that returns one good doc then nine terrible ones scores identically to one that returns ten good docs. Useless for multi-hop RAG, where you need several supporting chunks.

DCG · nDCG Järvelin & Kekäläinen, 2002

The workhorse of graded-relevance ranking. Gain grows with the relevance grade, discounted logarithmically by rank, then normalised by the perfect ordering so scores are comparable across queries.

DCG@k = Σi=1..k (2^reli − 1) / log₂(i + 1) exponential-gain form (standard) IDCG@k = DCG@k of the ideally sorted list nDCG@k = DCG@k / IDCG@k ∈ [0, 1] Discounts: rank 1 → 1/1.00 rank 2 → 1/1.58 rank 3 → 1/2.00 rank 10 → 1/3.46 Grades typically 0–3 or 0–4, so a "perfect" doc at rank 1 is worth (2⁴−1)/1 = 15.
whereWeb search, e-commerce ranking, reranker evaluation, BEIR / MTEB leaderboards (nDCG@10 is the default there).
whenRelevance is graded, and there are many degrees of "sort of useful."
whyIt's the only classic metric that handles graded labels and position discount together, and it's normalised so you can average across queries with different numbers of relevant docs.

Two forms exist — linear gain reli and exponential 2^rel−1. They give different numbers; say which you used. nDCG is also insensitive to redundancy: three near-identical chunks at ranks 1–3 score perfectly but give the LLM one fact. That gap is exactly why RAG needed its own metrics.

ERR — Expected Reciprocal Rank Chapelle et al., 2009

A cascade model: the user scans down and stops with probability proportional to the relevance of what they see, so a highly relevant doc at rank 1 discounts everything below it.

Ri = (2^reli − 1) / 2^relmax stop probability at rank i ERR = Σi=1..n (1/i) · Ri · Πj<i (1 − Rj)
whereCommercial web search evaluation; anywhere user behaviour is genuinely "scan until satisfied."
whenYou want a metric grounded in a user model rather than an arbitrary log discount.
whyCorrelates better with click behaviour than nDCG for navigational queries. Rarely used in RAG — the LLM reads all k chunks, so a cascade model is the wrong user model.

The judgements themselves: pooling and agreement

You cannot label a million documents per query. TREC's answer was pooling: run many systems, take the union of everyone's top-k, judge only that pool, treat unjudged as irrelevant. This biases against new systems that surface documents nobody pooled — which is exactly what happened when dense retrievers arrived and looked worse than they were on old TREC collections.

bpref Buckley & Voorhees, 2004

Designed for incomplete judgements: it counts only how often a judged-relevant doc is ranked above a judged-irrelevant one, ignoring unjudged documents entirely.

bpref = (1/R) · Σr [ 1 − |n ranked higher than r| / min(R, N) ] R = # judged relevant, N = # judged irrelevant
whereSparse-label settings — which includes most enterprise RAG golden sets you'll ever build.
whenYou have labels for a handful of docs per query and cannot assume the rest are irrelevant.
whyStops you from punishing a retriever for finding a good document your annotators never saw. Worth naming in an interview — it signals you've built a real golden set.
Cohen's κ · Fleiss' κ · Krippendorff's α

Inter-annotator agreement, corrected for chance. If your humans don't agree with each other, no model can be scored against them — and this is the same formula you'll later use to validate an LLM judge.

κ = (po − pe) / (1 − pe) po = observed agreement, pe = agreement expected by chance Cohen's κ → exactly 2 raters, nominal labels Fleiss' κ → 3+ raters Krippendorff's α → any # raters, missing data, ordinal/interval scales Rough reading: <0.2 poor · 0.2–0.4 fair · 0.4–0.6 moderate 0.6–0.8 substantial · >0.8 near-ceiling
whereAnnotation QA, rubric design, and — critically — judge validation in modules 6–8.
whenBefore you spend money labelling 5,000 examples. Pilot on 50 with 3 raters first.
whyκ < 0.4 means your rubric is ambiguous, not that your raters are bad. Fix the rubric.
Kendall's τ · Spearman's ρ

Rank correlation between two orderings — used to ask "does my cheap metric rank systems the same way my expensive metric does?"

τ = (C − D) / (n(n−1)/2) C = concordant pairs, D = discordant ρ = 1 − 6·Σdi² / (n(n²−1)) d = difference in ranks
whereMeta-evaluation: "does BLEU agree with humans?", "does my LLM judge rank the same as my annotators?"
whenYou're validating a proxy metric, not a system.
whyA proxy that gets absolute values wrong but rankings right is still usable for model selection. τ tells you that; MAE doesn't.

"For a RAG retriever, do you optimise precision or recall?"

Recall@k first, precision second, and the answer changes with context-window economics. If the answer-bearing chunk is missing, the generator cannot recover — that's an unrecoverable failure. Extra irrelevant chunks are recoverable: a strong model ignores them. So set k as large as latency and cost allow, maximise Recall@k, then use a reranker to raise precision within that budget. The nuance that earns the point: past a certain k, precision starts mattering again because of distraction and lost-in-the-middle effects, so you tune k empirically against end-to-end answer correctness, not against a retrieval metric.

1990–2015

Traditional ML: thresholds, probabilities, and drift

Supervised learning brought two ideas that IR didn't have: models emit scores, not sets, so the threshold is a separate decision from the model; and models decay, so evaluation is a monitoring problem, not a one-off. Both ideas transfer directly to guardrail classifiers and LLM routers today.

Classification

Accuracy · Balanced accuracy · MCC

Accuracy is the default and the trap. With 1% positives, predicting "negative" always scores 99%. Balanced accuracy averages per-class recall; MCC (Matthews correlation) uses all four cells of the confusion matrix and is the most honest single number for imbalanced binary problems.

Acc = (TP + TN) / (TP + TN + FP + FN) BalAcc = ½ · ( TP/(TP+FN) + TN/(TN+FP) ) mean of sensitivity & specificity MCC = TP·TN − FP·FN ───────────────────────────────────────── √( (TP+FP)(TP+FN)(TN+FP)(TN+FN) ) MCC ∈ [−1, 1]. 0 = random. 1 = perfect. −1 = perfectly inverted.
whereAny classifier: churn, fraud, PII detection, toxicity guardrails, intent routing.
whenUse accuracy only when classes are roughly balanced and error costs are symmetric. Otherwise MCC or per-class P/R/F1.
whyMCC is high only when the model does well on both classes, so it can't be gamed by the majority class.
ROC-AUC signal-detection theory, 1940s → ML, 1990s

Plot TPR against FPR across every possible threshold; the area underneath is the probability that a randomly chosen positive scores above a randomly chosen negative. It's threshold-free — a property of the model's ranking, not of any decision rule.

TPR = TP/(TP+FN) FPR = FP/(FP+TN) AUC = P( score(x⁺) > score(x⁻) ) = normalised Mann–Whitney U 0.5 = random · 0.7 fair · 0.8 good · >0.9 suspicious (check for leakage)
whereModel comparison and selection, credit risk, medical triage, ad ranking.
whenYou haven't chosen an operating threshold yet, and classes aren't extremely imbalanced.
whyLets you compare two models before committing to a business threshold, and is invariant to class prior shifts.

With 0.1% positives, ROC-AUC stays optimistic because FPR has a huge denominator — 1,000 false positives out of a million negatives barely moves FPR but destroys precision. Use PR-AUC in the rare-positive regime.

PR-AUC / Average Precision

Same idea, precision plotted against recall. The baseline is the positive class prevalence, not 0.5 — an AP of 0.30 on a 2%-positive problem is a 15× lift.

AP = Σn (Rn − Rn−1) · Pn step-wise, no interpolation (sklearn default) baseline AP = prevalence = positives / total
whereFraud, anomaly detection, information extraction, safety classifiers, needle-in-haystack retrieval.
whenPositives are rare and you only care about performance on the positive class.
whyPrecision is what the on-call human experiences. PR-AUC tracks it; ROC-AUC hides it.

Probability quality: the part people skip

Log loss · Brier score

Proper scoring rules — they're minimised only when the predicted probability equals the true probability, so they measure calibration and discrimination together.

LogLoss = −(1/N) Σi Σc yi,c · log(pi,c) Brier = (1/N) Σi (pi − yi)² binary case; ∈ [0,1], lower is better
whereAnywhere a downstream system consumes the probability — expected-value decisions, routing thresholds, abstention logic, cascade routers that send hard queries to a bigger model.
whenThe number itself is used, not just the argmax.
whyLog loss punishes confident mistakes brutally (−log(0.01) = 4.6). Brier is gentler and bounded, so it's more stable when a few predictions are near 0 or 1.
Calibration: reliability diagrams and ECE

Bin predictions by confidence and compare mean confidence to actual accuracy in each bin. A perfectly calibrated model sits on the diagonal: of everything it called 70% likely, 70% happened.

ECE = Σm=1..M (|Bm| / n) · | acc(Bm) − conf(Bm) | MCE = maxm | acc(Bm) − conf(Bm) | worst-bin, for safety-critical Fixes: Platt scaling (fit a sigmoid on a holdout) Isotonic regression (non-parametric, needs more data) Temperature scaling (single T on logits — the standard for neural nets)
whereRisk models, medical, and now LLM confidence: "should this agent escalate to a human?" is a calibration question.
whenWhenever you set a threshold for abstention, escalation, or auto-approval.
whyModern deep nets are systematically over-confident. An uncalibrated 0.9 threshold means something different after every retrain.

ECE is sensitive to the number of bins and can be near-zero for a model that's uninformative but honestly says 0.5 everywhere. Always report it next to AUC — calibration without discrimination is worthless.

Regression and forecasting

MAE · RMSE · MAPE · sMAPE · MASE · R²

whereDemand forecasting, pricing, latency/cost prediction, capacity planning.
whenRMSE if large errors are disproportionately costly; MAE if not. MASE for cross-series comparison — it's scale-free and doesn't explode near zero.
whyChoosing RMSE vs MAE is implicitly choosing whether you're predicting a mean or a median. Say so out loud in an interview.

Validation design — where most real errors live

The metric is rarely the problem; the split usually is.

  • Hold-out — one split, fast, high variance. Fine above ~50k rows.
  • k-fold / stratified k-fold — k=5 or 10; stratify on the label for imbalance.
  • Grouped k-fold — when rows share an entity (patient, customer, document). Without it, the same entity appears in train and test and you leak.
  • Nested CV — outer loop estimates performance, inner loop tunes hyperparameters. Skipping this means your reported score includes selection bias.
  • Time-series / walk-forward split — train on [0,t], test on (t, t+h], roll forward. Never shuffle time. Add an embargo gap if features have lookback windows.

Leakage checklist: target-derived features, post-outcome timestamps, duplicated rows across splits, fitting the scaler/encoder before the split, using future aggregates, and — in the LLM era — benchmark text present in pretraining data.

Statistical significance

Bootstrap CI: resample the test set with replacement B=1000×, recompute the metric each time, take the 2.5th and 97.5th percentiles. Use the paired bootstrap (same resampled indices for both models). McNemar's test — two classifiers, same test set, binary correct/incorrect: χ² = (|b − c| − 1)² / (b + c) b = A right & B wrong, c = A wrong & B right. Only disagreements count. Permutation test — shuffle the model labels between systems 10k times, see how often the observed gap appears by chance. No distributional assumption. Multiple comparisons — testing 20 variants at α=0.05 gives you ~1 false winner by construction. Apply Holm–Bonferroni or Benjamini–Hochberg (FDR).

Drift and monitoring: evaluation after deployment

PSI · KL · JS · KS

Ground truth arrives late or never, so you monitor the inputs and outputs for distribution change as a leading indicator.

PSI = Σi (ai − ei) · ln(ai / ei) a = actual %, e = expected % per bin <0.10 stable · 0.10–0.25 investigate · >0.25 significant shift KL(P‖Q) = Σ P(x) log( P(x)/Q(x) ) asymmetric, unbounded, blows up on zeros JS(P,Q) = ½KL(P‖M) + ½KL(Q‖M), M=½(P+Q) symmetric, bounded, √JS is a metric KS = supx |FP(x) − FQ(x)| continuous univariate, nonparametric
whereFeature monitoring, embedding drift, prompt-distribution drift, and output drift for LLM apps (response length, refusal rate, tool-mix).
whenContinuously in production; PSI weekly on top features is the standard enterprise pattern.
whyDistinguishes data drift (inputs moved) from concept drift (the input→output relationship moved). Data drift you can often ignore; concept drift always needs a retrain.

Drift is not degradation. A feature can shift a lot with no accuracy loss, and accuracy can collapse with no visible input drift. Drift alerts are triage signals, not incidents. With enough traffic, every KS test is significant — use effect sizes and thresholds, not p-values.

Fairness metrics — one line each

Demographic parity P(ŷ=1 | A=a) equal across groups Equal opportunity TPR equal across groups Equalized odds TPR and FPR both equal across groups Predictive parity PPV (precision) equal across groups Disparate impact ratio of selection rates; <0.8 is the classic "4/5ths rule" flag Impossibility result: with unequal base rates you cannot satisfy calibration, equal FPR and equal FNR simultaneously. You must choose.

Tooling: scikit-learn (metrics), MLflow (tracking + model registry), Evidently and NannyML (drift/monitoring), Great Expectations and Soda (data quality), deepchecks, Fairlearn / AIF360 (fairness). On Databricks specifically: Lakehouse Monitoring for drift and data quality, MLflow evaluate for model-level metrics.

"Your model's AUC is unchanged in production but the business says it got worse. What do you check?"

AUC is threshold-free and prior-invariant, so it can hold steady while the things people feel move a lot. Check, in order: (1) class prevalence — if positives halved, precision at your fixed threshold halved with it while AUC didn't budge; (2) calibration — a retrain can shift the score distribution so the old threshold now sits somewhere else on the curve; (3) segment-level performance — overall AUC can be flat while a growing segment collapses (Simpson's paradox); (4) label delay — you may be scoring on a biased, quickly-resolved subset; (5) whether "worse" means a metric at all, or means latency, coverage, or a changed downstream policy.

2002–2020

Text generation: from n-gram overlap to learned similarity

Machine translation forced the first automatic evaluation of free text. The whole family assumes one or a few reference answers exist and that a good output resembles them. That assumption is what broke when LLMs arrived — but these metrics are still correct and cheap for constrained generation, and interviewers use them to test whether you know why they were abandoned.

BLEU Papineni et al., IBM, 2002

Modified n-gram precision against one or more references, geometrically averaged over n=1..4, with a brevity penalty to stop the model from emitting three safe words.

clipped count: a candidate n-gram counts at most as often as it appears in any single reference. pn = Σ clipped matches of n-grams / Σ candidate n-grams BP = 1 if c > r e^(1 − r/c) if c ≤ r c = candidate len, r = ref len BLEU = BP · exp( Σn=1..N wn · log pn ) usually N=4, wn=¼ Note: if any pn = 0 the whole score is 0 → BLEU is corpus-level, not sentence-level. Use sacreBLEU for reproducible tokenisation.
whereMachine translation, code translation, deterministic format conversion, SQL generation (alongside execution accuracy).
whenThe output space is genuinely narrow and you have real references. Corpus-level comparisons only.
whyFree, instant, reproducible, and historically correlated ~0.6–0.8 with human MT judgements at the corpus level.

Precision-only, so it ignores information you failed to include. Zero credit for correct paraphrase. Meaningless on a single sentence. Tokenisation-dependent — two papers reporting "BLEU 34" may not be comparable at all.

ROUGE Chin-Yew Lin, 2004

BLEU's recall-oriented sibling, built for summarisation: did the summary cover what the reference covered?

ROUGE-N = Σref Σn-gram match / Σref Σn-gram count recall over references ROUGE-1 = unigram overlap · ROUGE-2 = bigram overlap ROUGE-L uses the Longest Common Subsequence (order-aware, gap-tolerant): Rlcs = LCS(X,Y)/|Y| Plcs = LCS(X,Y)/|X| Flcs = (1+β²)·R·P / (R + β²·P) ROUGE-Lsum — LCS computed per sentence then aggregated (the summarisation default)
whereSummarisation benchmarks (CNN/DailyMail, XSum), extraction coverage checks, meeting-notes QA.
whenYou care about coverage of required content and you have reference summaries.
whyCheap regression signal. Still useful as a guardrail: a sudden ROUGE-1 drop after a prompt change means content went missing, even if you no longer trust it as a quality score.

Extractive systems that copy sentences beat abstractive ones that write better summaries. ROUGE cannot see factual errors at all — a summary that inverts a negation scores almost identically.

METEOR · chrF · TER · WER
METEOR (2005): unigram alignment allowing stems, synonyms, paraphrase. Fmean = 10·P·R / (R + 9·P) recall weighted 9× Penalty = 0.5 · (chunks / matches)³ fragmentation METEOR = Fmean · (1 − Penalty) chrF (2015): character n-gram F-score (β=2). Strong for morphologically rich languages and robust to tokenisation. Good default over BLEU. TER: edit distance in words — (insert+delete+substitute+shift) / ref length. WER (speech): (S + D + I) / N. Can exceed 1.0. CER is the same at character level.
whereMETEOR/chrF for MT; TER for post-editing effort estimation; WER/CER for ASR, OCR and document-extraction pipelines.
whenWER is the one you'll actually reach for in enterprise work — any speech or scanned-document ingestion stage needs it.
whyEdit-distance metrics map to human effort: TER ≈ "how much would a human have to fix."
Perplexity

The exponentiated average negative log-likelihood — intuitively, the effective number of equally likely next tokens the model is choosing between.

PPL(X) = exp( − (1/N) · Σi=1..N log pθ(xi | x<i) ) equivalently: PPL = 2^H where H is cross-entropy in bits
wherePretraining and continued-pretraining monitoring, domain-adaptation checks, quantisation quality checks.
whenComparing checkpoints of the same model family on the same tokenizer and the same corpus. Nowhere else.
whyIt's the training objective, so it's the most sensitive early signal that something is going wrong.

Not comparable across tokenizers or corpora, and only weakly related to downstream usefulness — instruction tuning and RLHF often raise perplexity while making the model much more useful. Never quote perplexity as a product quality metric.

The learned-metric turn

BERTScore Zhang et al., 2019

Replace exact n-gram matching with greedy cosine matching between contextual token embeddings, so paraphrase gets credit.

Embed candidate x̂ and reference x with a contextual encoder. RBERT = (1/|x|) Σxi∈x maxx̂j xiTx̂j PBERT = (1/|x̂|) Σx̂j∈x̂ maxxi xiTx̂j FBERT = 2·P·R/(P+R) Optional IDF weighting; scores are rescaled against a baseline because raw cosine sits in a narrow band (~0.85–0.95).
whereSummarisation and generation eval where paraphrase is legitimate; still common as a cheap semantic-regression check in RAG pipelines.
whenYou have references, want more than lexical overlap, and can't afford an LLM judge on every row.
whyRoughly 2 orders of magnitude cheaper than judge calls, and much better correlated with humans than BLEU/ROUGE.

Still blind to factuality and to negation — "the drug reduced mortality" and "the drug did not reduce mortality" embed very close together. Never use it as a hallucination check.

BLEURT · COMET · MoverScore 2020

Fully learned metrics: a transformer fine-tuned on human quality ratings to predict the human score directly. COMET additionally conditions on the source text, not just the reference, and dominates modern MT evaluation.

BLEURT: BERT pretrained on synthetic perturbations, then fine-tuned on WMT human ratings → regression head predicting human score. COMET: encodes (source, hypothesis, reference) → estimator head. COMET-QE / CometKiwi drop the reference entirely → "quality estimation", the first reference-free neural metric. MoverScore: Word Mover's Distance over contextual embeddings (soft alignment rather than greedy 1-1 matching).
whereProduction MT, localisation QA. Historically important as the bridge to LLM-as-judge.
whenThere's a well-defined task with enough human ratings to train on.
whyReference-free quality estimation (COMET-QE) is conceptually the direct ancestor of everything in module 6 — a model trained to predict human judgement, then used in place of humans.

Why this family stopped being enough

  • The one-reference assumption dies. For "explain our refund policy" there are thousands of correct answers and no reference set can enumerate them.
  • No factuality signal. Overlap and embedding similarity both score a confident fabrication highly if it's phrased like the reference.
  • No instruction-following signal. Format, tone, refusal correctness, and constraint satisfaction are invisible.
  • Task diversity. One system now does summarisation, extraction, code, and dialogue; a single reference-based number can't span that.

What survived: exact match and F1-token for extractive QA, WER for speech, execution accuracy for code and SQL, and all of them as cheap regression detectors rather than quality scores.

"When would you still use ROUGE or BLEU in 2026?"

Three honest cases. One: as a cheap, deterministic tripwire in CI — you don't believe the absolute value, but a 15-point drop after a prompt refactor tells you content vanished, at zero cost and zero latency. Two: constrained transformation tasks with real references — translation, format conversion, template filling. Three: as a cost-tiering layer, where the cheap metric screens thousands of rows and only ambiguous ones go to a judge or a human. The framing that earns the point: these are screening instruments now, not quality instruments.

Chunking and context: the evaluation nobody runs

Chunk strategy is usually chosen by vibes and never measured. Measurable proxies:

  • Answer-containment rate — fraction of golden questions whose supporting fact survives intact in at least one chunk. Compute this before you touch the retriever; it is a hard ceiling on recall.
  • Chunk attribution — for each golden answer, which chunk IDs are needed. Gives you gold labels for Context Recall in module 5.
  • Needle-in-a-haystack (NIAH) — plant a fact at varying depths in varying context lengths, measure retrieval accuracy as a heatmap. RULER (2024) generalises this to multi-needle, tracing and aggregation tasks, and showed most "128k context" models degrade far below their advertised length.
  • Redundancy rate — mean pairwise similarity within the retrieved top-k. High redundancy means your k slots carry fewer than k facts. This is the concrete answer to "nDCG is high but the answer is wrong."
Reranker evaluation
Report the lift, not the absolute: Δ nDCG@10 (rerank − first stage) Always alongside: p50 / p95 added latency, and $ per 1k queries. Typical shape: bi-encoder recall@50 → cross-encoder rerank → top-5 to LLM. The cross-encoder sees (query, doc) jointly so it's far more accurate and far more expensive — O(n) forward passes per query.
whereBetween vector search and the generator in almost every serious RAG stack.
whenRecall@50 is high but Recall@5 is not — that gap is precisely what a reranker fixes.
whyReporting reranker quality without its latency cost is the classic junior mistake. The metric is a Pareto point, not a scalar.

"How do you evaluate an embedding model for our domain?"

Don't quote the MTEB leaderboard — that's the tell of someone who hasn't done it. Build a domain golden set of 200–500 (query, relevant chunk) pairs mined from real user questions and SME review. Then compare candidates on Recall@k and nDCG@10 on that set, against a BM25 baseline. Add the operational axes that decide the choice in practice: embedding dimension and therefore index cost, max sequence length versus your chunk size, multilingual coverage, inference latency, whether it's an API or self-hosted, and the migration cost of re-embedding the whole corpus when you switch. Finish with the ceiling check: measure answer-containment after chunking first, because a better embedding model can't retrieve a fact your chunker split in half.

2023–2025

RAG evaluation

RAG's central insight for evaluation is decomposition. A wrong answer has three possible causes — the retriever missed, the generator ignored what it was given, or the generator invented something — and one end-to-end score can't tell them apart. Every RAG metric suite is a way of separating those three.

The RAG triad (TruLens framing, 2023)

query ──────────────► context ──────────────► answer │ Context Relevance │ Groundedness │ │ (retriever's fault) │ (generator invents) │ └──────────────── Answer Relevance ────────────┘ (did it address the question at all) All three pass → the answer is very likely correct. Any one fails → you know which component to fix.

Faithfulness measures grounding, not truth. A perfectly faithful answer to a wrong document is still wrong. And a correct answer drawing on the model's parametric knowledge scores as unfaithful. Pair it with Answer Correctness on your golden set.

CRAG's scoring is the one to remember in interviews: correct answers score +1, "I don't know" scores 0, and hallucinations score −1. The metrics people forget to define

  • Abstention correctness — of the questions that are genuinely unanswerable from the corpus, what fraction did the system decline? And of the answerable ones, how often did it wrongly decline? These are just recall and false-refusal rate on a labelled unanswerable slice.
  • Noise robustness — inject k irrelevant chunks into the context and measure the drop in answer correctness. Directly quantifies how much precision you can afford to trade for recall.
  • Counterfactual robustness — plant a contradictory or outdated document and see whether the model notices the conflict or picks arbitrarily.
  • Freshness — for time-sensitive corpora, the share of answers reflecting the current version of a document rather than a superseded one.
  • Cost and latency per answered question — always. p50 and p95, plus embedding + retrieval + rerank + generation + judging costs broken out.

"Walk me through evaluating a RAG system end to end."

Structure the answer in four layers and say the word "decompose" early. Data layer: chunk-level answer-containment rate, because it caps everything downstream. Retrieval layer: Recall@k and nDCG@k against a human-labelled golden set, ANN recall against brute force, redundancy rate in the top-k. Generation layer: faithfulness/groundedness, answer relevancy, citation precision and recall, refusal correctness on a deliberately unanswerable slice. System layer: answer correctness on the golden set, noise robustness, p95 latency, cost per query, and then online — deflection rate, thumbs-down rate, human escalation rate. Close with the governance point: the golden set is versioned, every judge is validated against human labels with κ reported, and the whole thing runs in CI on every prompt or index change.

2023–now

LLM-as-a-judge

The unlock that made everything after it possible: use a strong model to approximate a human rater. Zheng et al.'s MT-Bench paper (2023) showed strong judges agree with human preferences at roughly the rate humans agree with each other — about 80%. That's the whole justification, and it comes with a stack of well-catalogued biases you must be able to name.

The three judging modes

Pointwise — score one output on a rubric (binary, or 1–5). Interpretable, absolute, comparable over time. Highest variance; scores cluster at 4 and drift between model versions. Pairwise — "which is better, A or B?" (optionally with ties). Much lower variance, far more reliable. Gives you no absolute level, and needs O(n²) comparisons unless you fit Bradley–Terry / Elo. Reference-guided — judge sees a gold answer alongside the candidate. Highest agreement with humans; needs ground truth.
G-Eval Liu et al., 2023

Chain-of-thought judging with a probability-weighted score, which removes the coarseness of integer outputs.

1. Give the judge the criterion (e.g. "coherence"). 2. Ask it to generate the evaluation steps itself (auto-CoT). 3. Score with form-filling, then weight by the token probabilities: score = Σi=1..5 p(si) · si s ∈ {1..5}, p from logprobs Without weighting, judges emit "4" for almost everything and the metric has no resolution. With it you get a continuous score.
whereSummarisation, writing quality, tone, coherence — subjective axes with no reference.
whenYou need a continuous score and your provider exposes logprobs.
whyReported human correlation (Spearman ~0.51 on SummEval coherence vs ~0.3 for prior metrics) was the result that made judge-based eval mainstream.
Elo and Bradley–Terry Chatbot Arena, 2023

Bradley–Terry: P(A beats B) = 1 / ( 1 + e^(βB − βA) ) Elo scale: P(A beats B) = 1 / ( 1 + 10^((RB − RA)/400) ) 400 points apart ⇒ ~91% win probability Online update: R' = R + K·(S − E), K ≈ 4–32 Fit BT by maximum likelihood over all recorded comparisons — it is order-independent, unlike sequential Elo, so it's what arenas actually use. Validating the judge — the part that separates seniors from juniors

A judge is a classifier. Treat it as one and evaluate it with module 2's toolkit.

1. Sample 100–200 outputs, stratified to include known failure modes. 2. Have 2–3 humans label them against the same rubric the judge uses. 3. Measure human–human agreement first (Cohen's/Fleiss' κ). If κ < 0.6, the rubric is broken — fix it before blaming the judge. 4. Measure judge–human agreement: accuracy, κ, and — because failure classes are imbalanced — precision/recall on the "fail" class. 5. Set the operating point deliberately. A groundedness judge used as a production guardrail needs high recall on hallucinations; the same judge used as a release gate needs high precision so it doesn't block releases. 6. Re-validate whenever you change judge model, judge prompt, or domain. Target: judge–human κ ≥ human–human κ − 0.1. Report both numbers.

Practical rules for writing judges

  • Binary beats Likert. "Does every factual claim appear in the context? yes/no" is reproducible; "rate faithfulness 1–5" is not.
  • One criterion per call. Bundled rubrics produce a single blurred number and the judge silently over-weights one axis.
  • Give the failure definition, not the success definition. Judges are much better at spotting a specified defect than at rating abstract quality.
  • Force a rationale before the verdict. Verdict-then-rationale produces post-hoc justification and measurably worse agreement.
  • Pin the model version and store the judge prompt in version control. A silent provider upgrade will move every historical number.
  • Consider a jury (PoLL, 2024): three cheaper heterogeneous judges voting often beat one frontier judge, at lower cost and with less self-preference.
  • Budget the cost. Judging is inference. On a 1,000-row golden set with 4 criteria and order-swapping, that's 8,000 calls per eval run.

"How do you know your LLM judge is right?"

"I validate it like any other classifier." Then give the loop: build a human-labelled meta-eval set stratified over known failure modes; measure human–human agreement first to establish the ceiling; measure judge–human agreement with κ and with precision/recall on the failure class; choose the operating threshold from the cost of the two error types in this use case; and re-run that validation whenever the judge model, prompt or domain changes. Add the honest limit: the judge is a proxy with a known error rate, so I report it as a distribution with a confidence interval and I never gate a release on a judge score alone without a human spot-check of the boundary cases.

2023–2026

Agents and tool calling

The object being evaluated changes shape. A RAG system produces one output; an agent produces a trajectory — a sequence of decisions, tool calls, observations and state changes, of variable length, with many valid paths to the same goal. Evaluation splits into outcome (did it work) and process (did it work for the right reasons, at acceptable cost).

Outcome metrics

Task success rate · pass@k · pass^k

Success rate is the headline. pass@k measures whether any of k attempts succeeds — useful when a human filters candidates. pass^k measures whether all k independent attempts succeed, which is the reliability number that matters for autonomous deployment.

Success rate = successful tasks / total tasks Success defined by: final-state check, execution test, exact match, or rubric judgement — declare which. pass@k = Etasks [ 1 − C(n − c, k) / C(n, k) ] n = samples generated, c = # correct among them. Unbiased estimator (Codex paper, 2021). Optimistic: assumes you can pick the winner — true with a test suite, false without one. pass^k = E [ C(c, k) / C(n, k) ] τ-bench, 2024 probability that k independent trials ALL succeed. Collapses fast: 80% per-trial success ⇒ pass^5 ≈ 0.33. This is the number to quote when someone asks "can we let it run unsupervised?"
whereCoding agents (SWE-bench), customer-service agents (τ-bench), workflow automation, data-engineering agents.
whenpass@k when a human or a verifier picks from candidates; pass^k when the agent acts alone.
whyA single-run success rate massively overstates autonomous reliability. Showing you know the difference is a strong senior signal.

Multi-turn and policy compliance

Single-turn tool eval misses most of what breaks in production. The multi-turn additions:

  • Instruction retention — a constraint given at turn 2 still honoured at turn 12.
  • State tracking — the agent's belief about the world matches the environment's actual state.
  • Clarification behaviour — asks when the request is genuinely underspecified, doesn't ask when it isn't. Both directions are failures; measure both.
  • Policy compliance — τ-bench's contribution: the agent has a domain policy document (refund rules, escalation rules) and success requires both the right end state and no policy violation on the way.
  • User simulation — an LLM plays the user from a persona and goal. This is how you get multi-turn coverage at scale, and the simulator itself needs validating: does it produce realistic distributions of ambiguity, correction and frustration?

Grading trajectories with a judge

ORM (outcome reward model) — grades only the final result. Cheap, unambiguous, but gives no credit assignment and rewards lucky paths. PRM (process reward model) — grades each step. Enables credit assignment, step-level debugging, and search (best-of-n over steps). Expensive to label. Practical hybrid used in industry: deterministic checks for what can be checked (final DB state, tests pass, schema valid, no forbidden tool touched) + rubric LLM judge over the trace for what can't ("did it verify before writing?", "did it escalate per policy?") + human review of a sampled 5–10% to keep the judge honest.

"How do you evaluate an agent when there's no single right answer and no reference trajectory?"

Say that you evaluate the end state and the constraints, not the path. Define success as a programmatic assertion over the world after the run — the record exists with these fields, the tests pass, the file matches this schema. Then layer constraint checks that are also deterministic: no forbidden tool was called, no PII left the boundary, the step and cost budget held, it terminated. Then use a rubric judge over the trace for the qualitative requirements you can't assert — did it verify before mutating, did it escalate when policy required. Then report reliability as pass^k rather than a single-run rate, and stratify results by an error taxonomy built from reading real failures, so the number tells you what to fix. Finish on cost per resolved task, because that's what determines whether it ships.

2025–2026

Skills, multi-agent systems, and production evaluation

The newest layer, and the one with the least settled vocabulary — which makes it the best place to sound current. Agents stopped being monoliths: capability now arrives as loadable skills, work is split across multiple agents, and the deciding metrics have moved from offline benchmarks to production telemetry.

Evaluating skills

A skill is a packaged unit of procedural capability — instructions, scripts and resources that an agent loads on demand when a task matches its description. Because loading is triggered by matching a request against skill descriptions, skill selection is a retrieval problem and module 1's metrics apply directly.

— Discovery / triggering (this is IR) — Trigger recall = tasks where the right skill loaded / tasks needing it Trigger precision = correct loads / total loads False activation rate = skill loaded when not needed / total tasks Selection accuracy @ N skills — measure the curve as the library grows; this is where skill libraries actually fail — Adherence — Procedure adherence = required steps executed / required steps (rubric judge over the trace against the skill's own written procedure) Constraint violations per run — the "never do X" clauses — Value — Task lift = success rate with skill − success rate without Paired on identical tasks. If lift ≈ 0, the skill is context cost with no return. Context overhead = tokens loaded per invocation, and $ per task delta Regression suite — every skill owns a small golden set; a skill edit reruns it plus the cross-skill suite that checks it didn't steal triggers from a neighbouring skill.

The failure mode specific to skill libraries: trigger interference. Adding skill 12 degrades skill 7 because their descriptions overlap. That's why the cross-skill regression suite matters more than any individual skill's own tests, and why description-writing is an eval-driven activity.

Multi-agent systems

Routing / delegation accuracy = tasks sent to the right sub-agent Handoff fidelity — is the context passed complete and uncorrupted? Measure downstream task success conditioned on handoff. Blame assignment — per-agent attribution of end-to-end failures. Requires span-level tracing; without it you cannot debug. Coordination overhead = total tokens (multi-agent) / tokens (single agent) for the same task. Often 3–15×. Justify it with a lift number. Deadlock / livelock rate, infinite-handoff rate Consistency — do two agents reach contradictory conclusions from the same evidence? MAST (2025) — a failure taxonomy for multi-agent systems, grouping errors into specification issues, inter-agent misalignment, and task verification failures. Use it as the label set for your error taxonomy rather than inventing one.

The honest senior position: multi-agent adds cost, latency and failure surface, so the eval must show a lift over a strong single-agent baseline on the same tasks. Most internal systems have never run that comparison. Saying you would is a differentiator.

Context engineering as an eval target

  • Effective context length — measured with RULER-style probes, not the vendor's spec sheet.
  • Compaction fidelity — after summarising a long history, what fraction of decision-relevant facts survive? Test by asking questions answerable only from the pre-compaction history.
  • Memory read/write correctness — precision and recall of what got stored, and whether stale memories are retrieved over fresh ones. Plus staleness: how often does the agent act on a superseded fact?
  • Position sensitivity — same information at the start, middle and end of context; the accuracy delta is your lost-in-the-middle penalty.

Online evaluation

A/B test — random assignment, one primary metric declared in advance, guardrail metrics that can only stop a launch (latency, cost, error rate, safety incidents). Power the test before running it: n per arm ≈ 16 · σ² / Δ² (rough, 80% power, α=0.05, two-sided) Use CUPED or covariate adjustment to cut variance with pre-period data. Interleaving — for ranking changes: blend two rankers' results into one list and attribute clicks. ~10–100× more sensitive than an A/B test, so it needs far less traffic. Retrieval-only; can't evaluate a generator. Shadow / canary — run the new system on live traffic without serving it (shadow) or serve to 1–5% (canary), compare distributions before full rollout. Sequential testing — always-valid p-values / mSPRT if you want to peek continuously without inflating false positives.

Safety, robustness and guardrail evaluation

Attack success rate (ASR) = successful attacks / attempts Attack families: direct jailbreak, prompt injection (indirect, via retrieved content or tool output), data exfiltration, tool misuse, privilege escalation. Utility-under-attack — AgentDojo's framing: report benign task success AND attack success together. A guardrail that blocks every attack by refusing everything has ASR 0 and utility 0. Guardrail classifier eval — it's a classifier (module 2): recall on the harmful class (misses are incidents) false positive rate (over-blocking silently destroys the product) Report the ROC and pick the operating point from the cost asymmetry. Over-refusal — measured on a benign-but-sensitive-looking set; the most under-measured failure in enterprise deployments. Robustness — paraphrase invariance, typo/noise tolerance, order-of-options invariance in MCQ, prompt-format sensitivity.

Benchmark hygiene: contamination and saturation

  • Contamination. Public benchmarks leak into pretraining. Detect with canary strings, n-gram overlap against training corpora, or the ordering test — if a model scores much better on a benchmark's original ordering than a shuffled variant, it has memorised it.
  • Saturation. Once the top of the leaderboard is within noise of the human ceiling, the benchmark no longer discriminates. This is why the field keeps building harder sets.
  • Private held-out slices. Keep 20–30% of every golden set out of any prompt, any fine-tune and any shared doc. Rotate it.
  • Construct validity. Ask whether the benchmark measures the capability you care about or a correlated artifact. Most published agent benchmarks correlate weakly with your enterprise workflow, which is the argument for building your own set.

Evals in CI

Treat evals as tests, with realistic tolerances: · pin model + version; record temperature, seed, and prompt hash with every run · temperature 0 is NOT deterministic (batching, GPU non-determinism, MoE routing) · run N=3–5 and compare distributions, not single numbers · gate on a confidence-interval-aware threshold, not on a point estimate · tier the suite: fast deterministic assertions on every commit, judge-based suite nightly, full human-in-the-loop review per release · store every trace; a failing eval must link to the trace that failed · version the golden set alongside the code that uses it Observability: OpenTelemetry GenAI semantic conventions are the emerging standard for spans/traces; Langfuse, Arize Phoenix, LangSmith, W&B Weave, Braintrust and MLflow all consume them.

"We're deploying agents across 65 markets. How do you evaluate that at scale?"

Separate what generalises from what doesn't. Shared: the harness, the error taxonomy, the judge prompts, the safety and tool-correctness suites, the telemetry schema — build these once. Per-market: the golden set, because language, regulation, product catalogue and escalation policy all differ; and the thresholds, because acceptable refusal and escalation rates differ by regulatory regime. Then run a small stratified golden set per market (100–200 items, SME-authored) plus one large shared set, and monitor per-market online metrics with the same dashboard so you can see divergence early. The organisational point that lands well: the bottleneck is never the metric, it's SME labelling capacity, so you invest in a review app that makes labelling take a minute and you spend judges on scale while spending humans on validating the judges.

Statistics and golden-set construction

Two questions decide whether any number above means anything: how many examples do I need, and where did the examples come from. Most eval work in industry is wrong at the second one.

How many examples?

For a success rate p̂ over n independent examples: 95% CI ≈ p̂ ± 1.96 · √( p̂(1−p̂)/n ) n = 30 → ±18pp (a demo, not a measurement) n = 100 → ±10pp n = 400 → ±5pp n = 1000 → ±3pp n = 2500 → ±2pp (worst case at p̂=0.5; tighter near 0 or 1. Use Wilson intervals at the extremes.) To detect a Δ between two systems, PAIR them on the same items and test only the disagreements — McNemar. This typically cuts required n by 4–10× because the item-difficulty variance cancels. Rule of thumb: 100 well-chosen, failure-mode-stratified examples beat 1,000 randomly sampled easy ones. Sample for coverage of the taxonomy, then reweight to the production distribution when reporting.

Building the golden set

  1. Start from real traffic. Pull 200 real sessions. If there's no traffic yet, have SMEs write the 50 questions they'd actually ask, then have a different SME answer them.
  2. Read them by hand. There is no substitute. Cluster the failures into 5–10 named modes. This taxonomy is the most valuable artifact you'll produce.
  3. Stratify. Sample deliberately across the taxonomy, plus deliberate slices: unanswerable questions, multi-hop questions, adversarial/injection attempts, ambiguous questions needing clarification, out-of-scope requests, and the highest-frequency head queries.
  4. Write ground truth carefully. For RAG, record both the answer and the chunk IDs that support it — that gives you Context Recall labels for free.
  5. Synthetic data with human filtering. LLM-generated question sets are fine for scale and terrible unaccompanied. Generate 10×, have SMEs keep the 1× that are realistic. Never let a synthetic set be the only set — it inherits the generator's blind spots.
  6. Version it. Golden sets change; scores across versions are not comparable. Tag every result with the set version.
  7. Hold out a private slice and keep it out of prompts, few-shot examples and fine-tunes.

Slice-based reporting

An aggregate score hides everything that matters. Report per-slice — by query type, document source, language, market, user segment, question difficulty, and time period — and set the alert on the worst slice, not the mean. This is how Simpson's paradox gets caught before a stakeholder catches it for you.

Minimum reporting standard for any eval result: metric name and exact definition · dataset name and version · n model + version + temperature · prompt hash · judge model + judge prompt hash point estimate + 95% CI · per-slice breakdown · date of run

Rapid fire

"Retrieval metrics improved but answer quality dropped. Explain."

Most likely redundancy: the reranker promoted near-duplicates, so nDCG rose while the number of distinct facts in context fell. Other candidates: k grew and the extra chunks became distractors (noise sensitivity); the answer-bearing chunk moved from position 1 to position 6 and hit the lost-in-the-middle effect; or the retrieval labels were LLM-generated and drifted away from what humans consider relevant. Diagnose by measuring intra-list similarity in the top-k, and by an ablation that holds retrieval fixed and varies only position and k.

"Your eval says the new model is better; users say it's worse. What now?"

Assume the eval is wrong until proven otherwise, and check in this order: distribution mismatch — is the golden set representative of current traffic, or is it a year old? Slice regression — a big win on the head and a collapse on a small but vocal segment. Judge bias — if the new model is more verbose or better-formatted, a judge will prefer it while users find it slower to read. Unmeasured axes — latency, tone, refusal rate, formatting stability, none of which your quality metric covers. Novelty and change aversion — real, but the last hypothesis, not the first. Then close the loop: turn the complaints into labelled examples and add them to the golden set, so the next version of the eval catches what this one missed.

"How much should evaluation cost?"

Give a shape, not a number. A tiered budget: deterministic assertions are free and run on every commit; a judge-based suite of ~500 rows × 4 criteria × 2 orderings is ~4,000 calls, which at a small judge model is a few dollars per run and can run nightly; human review is the expensive tier, so it's spent on validating judges and on a sampled 5% of production, not on bulk grading. Then the framing that matters: eval cost is a fraction of the cost of shipping a regression into a regulated market, and the real constraint is SME time, not compute — so the design goal is to spend model calls to conserve human attention.

"What's the difference between evaluating a RAG system and an agent?"

RAG has one decision point and a fixed pipeline, so you decompose spatially — retriever, generator, and their interaction — and you can score a single output against a reference. An agent has a variable-length sequence of decisions with feedback, so you decompose temporally — outcome versus trajectory — and there's usually no reference path. That drives three changes: success becomes a programmatic assertion on end state rather than a comparison to a gold string; reliability needs pass^k rather than a single-run rate because the agent runs unsupervised; and cost and step-efficiency become first-class quality metrics because an agent can burn unbounded resources on its way to a right answer. The components underneath don't change — an agent's tool router is still scored with precision and recall from 1979.
