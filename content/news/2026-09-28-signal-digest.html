AI-Generated Code Is Already Competing With Human Code

12:41 · AI Engineer Paris 2026

Theme & Topic

AI-written code has moved from novelty to a mainstream, load-bearing share of production codebases. The talk examines how its quality compares to human code at scale and what that means for how code review itself needs to change.

Speaker

Daksh Gupta is co-founder and CEO of Greptile, an AI code review company. Greptile reviews pull requests for engineering teams and has built its own dataset on AI- vs. human-authored code quality.

🔮 dakshgup

Problem Statement

As agents write an ever-larger share of production code, engineering orgs lack visibility into whether that code can be trusted at scale — and manual, line-by-line code review doesn't scale to the commit volume top engineers (and agents) now produce.

Solution & Key Aspects

Drawing on Greptile's own review data across a million-plus monthly pull requests from major companies, Gupta argues AI-authored code is now roughly on par with human code on core quality metrics, but different tools fail in different, identifiable patterns — which argues for review approaches built around intent and blast radius rather than surface-level diffs.

  • Share of AI-authored PRs Greptile reviewed rose from under 1% to over a quarter within about a year
  • Comparable performance to human code on metrics like revert rate and bug severity, per Greptile's data
  • Different coding agents show distinct failure patterns (e.g., certain tools skew toward specific bug/vulnerability classes)
  • Review approach centered on blast-radius analysis and sandboxed browser agents to verify behavior, not just read the diff

Limitations & Challenges

The findings come from Greptile's own customer base and review pipeline, so they may not generalize to all engineering orgs or codebases, and a 12-minute talk necessarily leaves out methodology detail behind the headline numbers.

Key Takeaways & Next Steps

Stop treating "is AI code as good as human code" as a yes/no question — the more useful question is which failure modes each tool introduces. Expect code review to shift from manual line-by-line inspection toward automated, intent- and impact-based verification as agent-authored volume keeps rising.

Get Out of the Model's Way

19:01 · AI Engineer Paris 2026

Theme & Topic

How AI dev-tool builders should design products that scale with rapidly improving frontier models, rather than building rigid workflows and scaffolding around the limitations of today's model.

Speaker

Kevin Hou is Engineering Lead for Antigravity at Google DeepMind. He previously led product engineering at Codeium and Windsurf, worked on autonomous vehicles at Nuro, and studied computer science at Princeton.

🔮 khou22

Problem Statement

Many product decisions made to compensate for a weaker model's limitations become dead weight — or actively hold the product back — once the underlying model improves. Hou frames "getting out of the model's way" as the central design challenge for agentic IDEs.

Solution & Key Aspects

Hou describes Antigravity's shift toward letting an orchestrating agent dynamically spin up specialized subagents, listen for events across the IDE/browser/terminal, and generate custom interfaces on the fly — instead of routing everything through a single chat transcript that a human has to parse.

  • Agents that dynamically select and launch specialized subagents rather than following a fixed pipeline
  • Persistent event listeners so agents react to changes as they happen, not only on request
  • Generative UI/artifacts (not just chat replies) so agents can present structured, trackable output
  • Design principle: model capability gains should show up as immediate, visible product improvements, not get absorbed by scaffolding built for older models

Limitations & Challenges

The talk is framed from inside a Google DeepMind product built on frontier models the company controls directly, so some lessons may transfer less cleanly to teams building on third-party model APIs. Antigravity itself has also drawn public comparisons to (and criticism relative to) Windsurf since its release.

Key Takeaways & Next Steps

Build the thinnest scaffolding possible around your model so that when the model improves, your product improves for free. Invest in giving agents "senses" — browser control, event listeners, dynamic subagents — rather than only better prompts.

Self-Improving software factories: The new open source model

20:37 · AI Engineer Paris 2026

Theme & Topic

The emergence of the "software factory" as a new category of engineering infrastructure, and how such factories can be made self-improving and vendor-agnostic rather than a single closed product.

Speaker

Zach Lloyd is founder and CEO of Warp, the AI-native terminal and agentic development tool company.

🔮 zachlloyd

Problem Statement

Teams adopting coding agents lack a clear way to measure ROI, and letting every engineer run their own bespoke agent locally creates governance and security gaps. Meanwhile, no standard infrastructure yet exists for automating the full loop of engineering work end to end.

Solution & Key Aspects

Lloyd frames the "main loop of software engineering" — triage, specification, implementation, review, verification, shipping, monitoring — as the unit to automate, with factories built as version-controlled, model-agnostic infrastructure that a company runs and owns itself, and that improve over time via "observer" agents that score performance and submit PRs to tune the factory's own configuration.

  • The "main loop": triage → spec → implementation → review → verification → shipping → monitoring, framed as the automation target
  • "Observer" agents that evaluate the factory's output and open PRs to improve model choice, context, or skills — the self-improving piece
  • Factories defined as version-controlled code that companies own and host, not opaque SaaS
  • Warp's own recently open-sourced CLI used as a live case study for running a factory around a real project

Limitations & Challenges

The concept is new and demonstrated mainly on Warp's own open-source project so far. "Self-improving" is Lloyd's framing rather than an established, independently benchmarked term, and it assumes teams are ready to grant real autonomy — including PR-merge influence — to observer agents.

Key Takeaways & Next Steps

Treat the "software factory" as an infrastructure layer — owned, model-agnostic, version-controlled — not a single vendor's product. Expect a new engineering discipline ("meta-engineering": building and tuning the systems that build the product) to grow alongside traditional engineering roles.
